## 1. ESC1 — Web Server + Client Authentication added by mistake

### Primary-source facts

- Microsoft's default-template table lists **Web Server**: "Proves the identity of a Web server," Key usage = *Signature and encryption*, Subject type = *Computer*, **Published to AD DS = No**, Template version = **1**. [MS-PRIMARY] — [Certificate template concepts in Windows Server](https://learn.microsoft.com/en-us/windows-server/identity/ad-cs/certificate-template-concepts)
  - **Caveat:** "Published to AD DS" in this table means the CA auto-publishes *issued certificates* back to the subject's `userCertificate` AD attribute (`CT_FLAG_PUBLISH_TO_DS`, see §2 below) — it is **unrelated** to whether a template is enrollable by low-privileged principals or added to a CA's `certificateTemplates` list. Do not conflate the two. [INFERENCE from MS-CRTD flag semantics]
  - This table does **not** enumerate literal EKU OIDs per template — Microsoft has no published machine-readable "default EKU set per built-in template" document. The only MS-CRTD worked example (`certutil -v -dstemplate administrator`) dumps the **Administrator** template, not Web Server: `pKIExtendedKeyUsage = {1.3.6.1.4.1.311.10.3.1 (Trust List Signing), 1.3.6.1.4.1.311.10.3.4 (EFS), 1.3.6.1.5.5.7.3.4 (Secure Email), 1.3.6.1.5.5.7.3.2 (Client Auth)}`, `msPKI-Certificate-Name-Flag = 0xA6000000` (`SUBJECT_ALT_REQUIRE_UPN | SUBJECT_ALT_REQUIRE_EMAIL | SUBJECT_REQUIRE_EMAIL | SUBJECT_REQUIRE_DIRECTORY_PATH`). [MS-PRIMARY] — [MS-CRTD Structure Example](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-crtd/11f578e0-15ff-4d2c-86bb-206c50153d89). This confirms the *format* of the attribute (array of dotted OIDs) and exact bit-decomposition of the name-flag, but is the wrong template to source Web Server's literal default values from.
  - **GAP:** Web Server's literal default `pKIExtendedKeyUsage` (commonly believed to be Server Authentication only, OID `1.3.6.1.5.5.7.3.1`) is not stated in any Microsoft primary document found. Needs a lab `certutil -v -dstemplate WebServer` capture (or equivalent `Get-ADObject` read) against a reference AD CS install to confirm authoritatively. **Treat as GAP → lab observation required.**
- `msPKI-Certificate-Name-Flag` bit semantics (`CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT = 0x1`, plus all `SUBJECT_ALT_REQUIRE_*`/`SUBJECT_REQUIRE_*` bits) are fully enumerated with exact processing rules. [MS-PRIMARY] — [MS-CRTD: msPKI-Certificate-Name-Flag](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-crtd/1192823c-d839-4bc3-9b6b-fa8c53507ae1), [MS-WCCE: msPKI-Certificate-Name-Flag processing rules](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-wcce/a1f27ffb-7f74-4fa1-8841-7cde4ba0bcfe). Web Server templates conventionally use `CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT` (bit `0x1`, value sometimes just `1`) so the requester can supply the server's hostname as subject — this is the exact bit ESC1 depends on, per the whitepaper's formal ESC1 definition below.
- `pKIExtendedKeyUsage` is a multi-valued Unicode-string AD attribute (`attributeId 1.2.840.113556.1.4.1333`) holding the EKU OIDs embedded in issued certificates. [MS-PRIMARY] — [Win32 ADSchema: PKI-Extended-Key-Usage attribute](https://learn.microsoft.com/en-us/windows/win32/adschema/a-pkiextendedkeyusage). `msPKI-Certificate-Application-Policy` is the schema-v2+ analogue that the Certificate Templates MMC snap-in actually edits (both are generally kept in sync by the CA tooling; the whitepaper explicitly calls out `pKIExtendedKeyUsage` as *the* attribute controlling what a certificate is used for). [WHITEPAPER] — *Certified Pre-Owned* p.16-17 (Background → Certificate Templates): "`pKIExtendedKeyUsage` ... contains an array of OIDs enabled in the template ... include things like ... Client Authentication (OID 1.3.6.1.5.5.7.3.2)."
- **ESC1's formal definition** (verbatim technique table): "**ESC1** — Domain escalation via No Issuance Requirements + Enrollable Client Authentication/Smart Card Logon OID templates + `CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT`." [WHITEPAPER] — *Certified Pre-Owned* p.8-9 (Offensive Technique ID table), confirmed again in the dedicated ESC1 section (p.54-64) and its detection LDAP filter, which explicitly matches on `pkiextendedkeyusage=1.3.6.1.5.5.7.3.2` (and the equivalent Smart Card Logon/PKINIT/Any-Purpose OIDs) **together with** `mspki-certificate-name-flag:...:=1` (the `ENROLLEE_SUPPLIES_SUBJECT` bit) and no manager-approval/no-RA-signature requirement.
- The five EKU OID scenarios the whitepaper found actually enable domain authentication: Client Authentication (`1.3.6.1.5.5.7.3.2`), PKINIT Client Authentication (`1.3.6.1.5.2.3.4`, not present by default), Smart Card Logon (`1.3.6.1.4.1.311.20.2.2`), Any Purpose (`2.5.29.37.0`), and SubCA/no-EKU. [WHITEPAPER] p.21.

### Minimal override recommendation

- **Needed for the scenario to work:**
  1. Append `1.3.6.1.5.5.7.3.2` (Client Authentication) to the cloned Web Server copy's `pKIExtendedKeyUsage` **and** `msPKI-Certificate-Application-Policy` (both, to keep the schema-v2 GUI/engine consistent) — **append, don't replace**, so Web Server's existing (Server Authentication, presumably) EKU(s) survive, matching the "added by mistake" narrative (an admin *adds* Client Auth to an existing Web Server-derived template, they don't replace its purpose).
  2. Confirm `msPKI-Certificate-Name-Flag` already carries `CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT` (bit `0x1`) on the Web Server source (this is the standard reason Web Server templates let an admin type an arbitrary hostname) — if so, **no name-flag change is needed**; the mistake is purely the added EKU. This needs the lab-observation confirmation noted above as a GAP.
  3. Grant the two new ACEs per the approved table: Domain Users → Enroll extended right (`{0e10c968-78fb-11d2-90d4-00c04f79dc55}`) + Read (GenericRead/ReadProperty on all properties).
  4. Publish on the selected CA (add template CN to `certificateTemplates` on the Enrollment Services object — see §4 mechanics, identical across all four scenarios).
- **Inherited baggage to strip:** none identified from primary sources — Web Server's other defaults (key usage = signature+encryption, schema v1, no manager approval expected) are exactly what the scenario needs; no evidence a "strip" step is required beyond the clone-skip-list already in `Cloning-A-Template.md` (`cn, name, objectGUID, distinguishedName, whenCreated/Changed, uSNCreated/Changed, dSCorePropagationData, nTSecurityDescriptor, objectCategory, showInAdvancedViewOnly, displayName, msPKI-Cert-Template-OID` — the OID in particular **must** be regenerated per the cloning doc, confirmed necessary by that doc's own "Gotchas" section).

### Post-KB5014754 functioning note (secondary, flagged because it affects whether ESC1 "still works")

- Per [MS-WCCE name-flag processing rule 4](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-wcce/a1f27ffb-7f74-4fa1-8841-7cde4ba0bcfe): when `CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT` is set, the CA adds the SID security extension (`szOID_NTDS_CA_SECURITY_EXT`) **only if the client supplied it as an extension in the request** — unlike rule 2.v (AD-built subjects), where the CA **always** stamps the requestor's real `objectSid`. This means a classic ESC1 cert (attacker-chosen SAN, CA-supplied subject not used) will generally **lack** a correctly-populated SID extension and **lack** a strong `altSecurityIdentities` mapping, so under KB5014754 Full Enforcement (mandatory since Sept 9 2025) it would likely be **denied** unless the attacker also forges a matching SID extension into the CSR (a client-side capability, not CA policy-enforced per this rule's wording). [MS-PRIMARY] — [KB5014754](https://support.microsoft.com/en-us/topic/kb5014754-certificate-based-authentication-changes-on-windows-domain-controllers-ad2c23b0-15d8-4340-a468-4d4f3b188f16). **GAP:** whether common enrollment clients (certreq/Certify) can or do supply this extension, and whether the CA's default policy module (`certpdef.dll`) accepts client-supplied SID extensions on ENROLLEE_SUPPLIES_SUBJECT templates, is not documented by Microsoft and needs a lab check if the owner cares whether ESC1 "still bites" in the finished lab.

## 2. ESC4 — Web Server + Domain Users Full Control ("testing permissions left in place")

### Primary-source facts

- **ESC4's formal definition**, verbatim: "**Vulnerable Certificate Template Access Control-ESC4** ... if an attacker can chain access to a point that they can actively push a misconfiguration to a template that is not otherwise vulnerable (e.g., by enabling the `mspki-certificate-name-flag` flag for a template that allows for domain authentication) this results in the same domain compromise scenario as [ESC1]." The specific rights of concern are enumerated exactly: **Owner** (implicit full control), **FullControl**, **WriteOwner**, **WriteDacl**, **WriteProperty** (can edit any property). [WHITEPAPER] — *Certified Pre-Owned* p.70-72 (ESC4 section).
- This directly confirms the mechanism requested: granting `Domain Users` **Full Control** (`GenericAll`) on a certificate-template AD object is sufficient for the ESC4 "template reconfiguration" primitive, because FullControl is a superset of `WriteDacl`/`WriteOwner`/`WriteProperty`, any one of which already suffices per the whitepaper's own right-by-right breakdown.
- The companion **DPERSIST3** section gives the exact reconfiguration recipe the whitepaper itself demonstrates: grant `WriteOwner` → attacker takes ownership → attacker sets `mspki-certificate-name-flag = 1` (`ENROLLEE_SUPPLIES_SUBJECT`) on a template that already allows domain authentication → attacker enrolls specifying a DA SAN. [WHITEPAPER] p.93-94 ("Malicious Misconfiguration-DPERSIST3"). Since Web Server already carries an auth-capable EKU once ESC1's override is applied (or even on its own, if Web Server's own default EKU happens to include a domain-auth-capable OID — GAP, see §1), granting Domain Users **FullControl** on the "Test SSL" clone lets a low-priv principal flip `ENROLLEE_SUPPLIES_SUBJECT` and/or add a domain-auth EKU themselves at will — i.e., the ESC4 primitive is "the permission to recreate ESC1 (or worse) on demand," which is exactly the "testing permissions left in place" narrative.
- I found no Microsoft-authored document that uses the "ESC4" label (that taxonomy is SpecterOps's own, not Microsoft's); KB5014754 doesn't address template ACLs at all (it is specifically about DC-side strong certificate mapping enforcement, not template access control). The task brief's fallback citation ("Microsoft's own ESC4 guidance / AD CS security feature status page") does not appear to exist as a named Microsoft artifact — **the whitepaper is the correct and sufficient primary source for the mechanism**, consistent with the task's own allowance to cite SpecterOps directly.

### Minimal override recommendation

- **Needed for the scenario to work:** grant Domain Users `GenericAll` (ActiveDirectoryRights.GenericAll, AccessControlType.Allow, ObjectType = all-zero GUID) on the "Test SSL" clone's security descriptor. No attribute changes are required at creation time — the entire point is that the *template itself* starts in a plausible, otherwise-unremarkable Web Server-derived state and the vulnerability is **only** the ACL. (This matches the existing `Set-AGTemplateAce.ps1` `'FullControl|GenericAll'` branch already in the repo, modulo that cmdlet currently targets `Authenticated Users` only — see §0 note.)
- **Inherited baggage to strip:** none — ESC4's whole point is that the template is otherwise unremarkable; any pre-existing Web Server EKU/name-flag defaults are irrelevant to proving the primitive (an attacker who has FullControl can set whatever they want afterward). If the lab wants ESC4 to be *immediately* demonstrable without a second attacker-side write, the template should be left exactly as cloned (no name-flag/EKU override at template-creation time) so the ACE grant is unambiguously the sole vulnerability — consistent with "testing permissions left in place" (i.e., nothing else was changed).

## 3. ESC2 + schema-v1 User enrollment chain (VMware 6.x / SubCA clone)

### Is this really ESC2, or does it resemble ESC3? — primary-source answer: **it is ESC3's mechanism, bootstrapped by an ESC2-flavored source template**

- **ESC2's formal definition**, verbatim: "Domain escalation via No Issuance Requirements + Enrollable Any Purpose EKU or no EKU ... **While templates with these EKUs can't be used to request authentication certificates as other users without the `CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT` flag being present (i.e., ESC1), an attacker can use them to authenticate to AD as the user who requested them** ... In contrast, an attacker can use a certificate with no EKUs — a subordinate CA certificate — for any purpose as well but could also use it to sign new certificates." [WHITEPAPER] p.65-66 (ESC2 section). **The defining trait of pure ESC2 is direct self-authentication (or at worst, signing new certs if the SubCA is NTAuth-trusted) — it is a single-template, single-hop attack.**
- **ESC3's formal definition**, verbatim: two conditions across **two separate templates**: "Condition 1 — A template allows a low-privileged user to enroll in an enrollment agent certificate ... **The certificate template defines the Certificate Request Agent EKU** [1.3.6.1.4.1.311.20.2.1]." "Condition 2 — Another template permits a low privileged user to use the enrollment agent certificate to request a certificate on behalf of another user, and the template defines an EKU that allows for domain authentication ... **The template schema version 1** or is greater than 2 and specifies an Application Policy Issuance Requirement requiring the Certificate Request Agent EKU." [WHITEPAPER] p.66-69 (ESC3 section).
- The approved inventory's chain ("SubCA-derived template used for client auth/enrollment-agent purposes combined with a schema-v1 User template to perform an enroll-on-behalf-of attack") is **structurally ESC3**: two templates, a co-signing/agent step, and the schema-v1 target. **Distinguishing criterion applied:** ESC2 ends at step 1 (direct authentication with the SubCA-derived cert itself); ESC3 requires a second enroll-on-behalf-of hop into a *different* target template. Since the inventory explicitly routes through the **User** template as the second hop, this is ESC3's mechanism, not ESC2's. The inventory's own label ("ESC2 + schema-v1 User enrollment chain") already hints at this hybrid, and I recommend the human/report treat it as **ESC3, with the agent certificate sourced from an ESC2-shaped (no-EKU) template** rather than as pure ESC2. [INFERENCE drawn directly from the two verbatim whitepaper definitions above]

### VMware 6.x's no-EKU profile already satisfies the Certificate-Request-Agent requirement — no override needed

- The wire-format clause for "Request on Behalf of" reads: "**certificates**: This field MUST include all the certificates that are associated with the private keys used to sign the certificate request. **The certificates MUST have the certificate request agent EKU (1.3.6.1.4.1.311.20.2.1).**" [MS-PRIMARY] — [MS-WCCE 3.2.2.6.2.1.2.1.2 / linked page: Request on Behalf of Using CMS and CMC Request Format](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-wcce/92a48c37-2928-4800-9e91-40aad6a9bc3b).
- **Correction from an earlier draft of this report:** that MUST-clause reads literally as requiring explicit possession of the EKU, but Microsoft's actual EKU-checking semantics treat **total absence of the EKU extension as valid for all usages**, which includes Certificate-Request-Agent. This is confirmed by two independent, directly-on-point primary/corroborating sources, not merely inferred from the OID table:
  - **RFC 5280 §4.2.1.12** (cited verbatim by Microsoft's own CAPI2 documentation below): "If the extension is present, then the certificate MUST only be used for one of the purposes indicated." The MUST-restriction is conditional on the extension's *presence*; RFC 5280 makes no provision for a no-extension certificate to be restricted at all.
  - **Microsoft's CAPI2 EKU validation behavior**, confirmed by a Microsoft MVP (PKI) with a reproduced `X509Chain`/`certutil` test against a real no-EKU CA certificate: "Unlike other extensions like Name Constraints, EKU extension is not constrained by RFC... If EKU is totally absent in certificate extension, then certificate is literally valid for all usages. This behavior is made to be compatible with X.509 Version 1 certificates." [MS-ADJACENT/COMMUNITY-MVP, directly reproducing Microsoft API behavior] — Vadims Podāns (Microsoft MVP, PowerShell/PKI), [Constraining Extended Key Usages in Microsoft Windows](https://www.sysadmins.lv/blog-en/constraining-extended-key-usages-in-microsoft-windows.aspx). The article's own reproduced test shows a no-EKU CA certificate passing `X509Chain.Build()` cleanly in default mode, and even in "constrained" mode a no-EKU certificate in the chain imposes no restriction (only an explicit, narrowed EKU list via certificate-store properties does).
  - This is exactly why the whitepaper itself groups "**Any Purpose EKU or no EKU**" as functionally equivalent for ESC2 (already quoted above) — it is the same absence-means-unrestricted rule, not a coincidence of wording.
- **Corrected conclusion:** a plain SubCA clone with **no EKU override at all** (the literal ESC2 "no EKU" profile, exactly as the approved inventory specifies) already satisfies the MS-WCCE "MUST have the certificate request agent EKU" check, because Windows' EKU-checking code has no restriction to enforce against a no-EKU certificate. **No additional EKU override is needed on VMware 6.x for the chain to function.** A lab capture (issue an on-behalf-of request signed with a no-EKU agent cert against a real CA) would upgrade this from well-supported inference to directly observed fact, but is not required to unblock design.

### Schema-v1-specific mechanics (the "schema-v1 User template" half)

- Verbatim: "**If the certificate template's schema version is 1**, the CA will require signing certificates to have the Certificate Request Agent OID before issuing the certificate" — this is an *unconditional*, schema-version-driven CA behavior, distinct from schema-v2+ templates where the **same requirement must be explicitly configured** via `msPKI-RA-Application-Policies` (Application Policy Issuance Requirement) and `msPKI-RA-Signature` ("This number of authorized signatures"). [WHITEPAPER] p.31-32 ("Enrollment Agents, Authorized Signatures, and Application Policies"). Per the correction above, "have the Certificate Request Agent OID" is satisfied either by explicit possession or by EKU absence.
- Built-in `User` is schema version **1** per Microsoft's default-template table ("Template version: 1"). [MS-PRIMARY] — [Certificate template concepts](https://learn.microsoft.com/en-us/windows-server/identity/ad-cs/certificate-template-concepts). This is consistent with and explains the shared constraint "Publish the existing schema-v1 User template if needed. Do not change its ACL." — because schema-v1's enrollment-agent gate is baked into the CA's processing rule for that schema version, not into any editable template attribute, so there is nothing to misconfigure/override on `User` itself; the vulnerability is entirely in *who holds a valid agent certificate* and *what their enroll rights on `User` are*.
- `msPKI-RA-Application-Policies` (the schema-v2+ issuance-requirement attribute) is a documented, named MS-CRTD attribute (section 2.23 per the spec's table of contents) distinct from `msPKI-Certificate-Application-Policy` (the issued-certificate's own EKU list) — confirmed by its appearance as a named precondition in [MS-CERSOD Example 6](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cersod/97f47d4c-2901-41fa-9616-96b94e1b5435). [MS-PRIMARY]

### KB5014754 impact on whether this chain still functions

- The on-behalf-of CSR's `requestername` name-value pair "**MUST be used to construct the Subject field in the issued certificate**" [MS-PRIMARY] — [MS-WCCE: Request on Behalf of Using CMS and CMC Request Format](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-wcce/92a48c37-2928-4800-9e91-40aad6a9bc3b). Because `User` is a schema-v1, "build subject from Active Directory" template (not `ENROLLEE_SUPPLIES_SUBJECT`), the CA resolves `requestername` to a **real** target AD object and builds the subject/SAN/SID from that object's actual attributes, per the standard name-flag processing rules (§1) applied with `EndEntityDistinguishedName` = the resolved target user, not the agent. **[INFERENCE, moderately confident]** This means — unlike classic ESC1's attacker-chosen arbitrary SAN — the resulting certificate's SID security extension (added automatically per [MS-WCCE name-flag rule 2.v](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-wcce/a1f27ffb-7f74-4fa1-8841-7cde4ba0bcfe), since `User`'s name-flag is not `ENROLLEE_SUPPLIES_SUBJECT`) will contain the **real, correctly-matching `objectSid`** of the on-behalf-of target — satisfying KB5014754 Full Enforcement's strong-mapping bar automatically, with no attacker-side SID forgery needed. **This chain should still function under Full Enforcement (post-Sept-2025), unlike classic ESC1**, *provided* the target of the on-behalf-of request is a real, enabled AD account (e.g., a built-in Administrator or a domain admin), consistent with [KB5014754](https://support.microsoft.com/en-us/topic/kb5014754-certificate-based-authentication-changes-on-windows-domain-controllers-ad2c23b0-15d8-4340-a468-4d4f3b188f16)'s SID-extension mechanism. **GAP:** this specific identity-resolution behavior for on-behalf-of requests is not spelled out as explicitly as the direct-enrollment case in MS-WCCE's name-flag section; a lab capture of an actual issued on-behalf-of `User` certificate (checking for the `1.3.6.1.4.1.311.25.2` SID extension and its value) would upgrade this from inference to observed fact.
- `CT_FLAG_NO_SECURITY_EXTENSION` (`msPKI-Enrollment-Flag` bit `0x00080000`) is the only template-level override that would suppress the SID extension; `User`'s historical default (per `Cloning-A-Template.md`'s lab observation) does not set it, so the default behavior is "SID extension added." [LOCAL-OBSERVATION + MS-PRIMARY cross-reference] — [MS-CRTD: msPKI-Enrollment-Flag](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-crtd/ec71fd43-61c2-407b-83c9-b52272dec8a1).

### Minimal override recommendation

- **Needed for the scenario to work (VMware 6.x / agent leg):**
  1. Clone SubCA → VMware 6.x, **no EKU override** — the source's no-EKU profile already satisfies the Certificate-Request-Agent requirement (corrected above).
  2. Grant `Authenticated Users`: Read + Enroll on VMware 6.x.
  3. Publish VMware 6.x on the selected CA.
  4. Publish (or confirm already published) the built-in `User` template on the same CA, **ACL unchanged**, per the shared constraint. If `Domain Users`/`Authenticated Users` cannot enroll in `User` as-is, this is a documented prerequisite failure (per the issue's own "stop with a prerequisite error" instruction), not something to patch by editing `User`'s ACL.
- **Inherited baggage to strip:** SubCA's `pKIMaxIssuingDepth` and CA-capable flags are what make it "no EKU"/signing-capable in the first place, and are now also confirmed as exactly what makes it function as the Certificate-Request-Agent in this chain — per ESC2's own definition this is a feature of the scenario, not baggage, **provided** the clone is never added to NTAuthCertificates (not part of this scenario's recipe, and the shared constraints don't mention it — confirms it should stay un-added).

## 4. Unpublished ESC4 + ESC5 publication chain (Workstation Authentication → Copy of Workstation)

### Primary-source facts

- The **Enrollment Services** container and its `certificateTemplates` attribute are formally specified: "The object of type `pKIEnrollmentService` under `CN=Enrollment Services,CN=Public Key Services,CN=Services,CN=Configuration,DC=...` ... **The certificateTemplates attribute of this object is set with the list of names of the certificate templates that this CA issues**." [MS-PRIMARY] — [MS-WCCE: CA Information in the Active Directory](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-wcce/ad150321-4b89-4802-8713-6c7a51cc0b84). The attribute itself: `ldapDisplayName: certificateTemplates`, `attributeId: 1.2.840.113556.1.4.823`, multi-valued, each string identical to a template object's `cn`. [MS-PRIMARY] — [MS-WCCE: certificateTemplates Attribute](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-wcce/e820490d-10d7-421a-ba02-1226f893f61a).
- This **is** the "publish" mechanism, confirmed independently by the whitepaper: "Enterprise CA 'publishes' the template, making it available for clients to enroll in – by adding the template's name to the certificatetemplates attribute of an Enterprise CA's AD object." [WHITEPAPER] p.22, p.39.
- **ESC5's formal definition** explicitly names this as an abuse surface: "**Vulnerable PKI Object Access Control-ESC5** ... Several objects outside of certificate templates and the certificate authority itself can have a security impact ... Any descendant AD object or container in `CN=Public Key Services,CN=Services,CN=Configuration,...` (e.g., the Certificate Templates container, Certification Authorities container, the NTAuthCertificates object, **the Enrollment Services Container**, etc.) If a low-privileged attacker can gain control over any of these, the attack can likely compromise the PKI system." [WHITEPAPER] p.73. This directly confirms: Full Control on the Enrollment Services object (the pKIEnrollmentService object itself, which holds `certificateTemplates`) is sufficient to functionally "publish" a template, because the attacker can simply write the attribute themselves (exactly like `Publish-AGCertifcateTemplate.ps1` already does via `PutEx`), with no need for CA-service-level `ManageCA` rights.
- The task's shared constraint specifies granting Full Control on **"that CA's directory object that holds certificateTemplates"** (i.e., the Enrollment Services object, not the CA's registry-based `Security` descriptor used for request-time enrollment gating, which is a **separate** security surface covered by MS-CSRA, not MS-WCCE). [MS-PRIMARY] — the whitepaper explicitly distinguishes these two: "An Enterprise CA defines enrollment rights using a security descriptor as well ... This ultimately ends up setting the *Security* registry value in the key `HKLM\...\CertSvc\Configuration\<CA NAME>`" (p.25) vs. the AD-object-level DACL on the Enrollment Services object covered by ESC5. The task explicitly says "Do not substitute permissions on the CA host or service" — this matches, confirming the AD-object DACL (ESC5-style) is the correct target, not the registry/DCOM `ManageCA`/`ManageCertificates` rights (ESC7).

### Live-reload / timing question — primary-source-grounded partial answer + GAP

- Microsoft's own publish workflow (`Add-CATemplate`/GUI "New → Certificate Template to Issue") **does not mention any CertSvc restart requirement** for ordinary publish/unpublish operations. [MS-PRIMARY] — [Manage certificate templates in Windows Server](https://learn.microsoft.com/en-us/windows-server/identity/ad-cs/manage-certificate-templates), "Publish a template to a CA" section. By contrast, the **same document explicitly requires a CertSvc restart** only for the *rename* workflow: "If you published the template, remove it from every issuing CA, **restart the Active Directory Certificate Services service (CertSvc)** on the affected CAs, and publish the renamed template again." [MS-PRIMARY] — same doc, "Rename a custom template" section. The asymmetry (restart required for rename, not mentioned for publish/unpublish) is itself evidence that ordinary `certificateTemplates` list changes do **not** require a restart.
- Separately, MS-CERSOD confirms the CA **does** maintain a live LDAP change-notification subscription for certificate-template data: "The CA-WCCE server registers itself to receive change notifications ... when an attribute of a certificate template is being modified in order to stay up-to-date with any changes and to avoid retrieving the templates for each request." [MS-PRIMARY] — [MS-CERSOD Example 6](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cersod/97f47d4c-2901-41fa-9616-96b94e1b5435). This passage is scoped to a given `pKICertificateTemplate` object's own attributes (e.g., EKU edits), **not explicitly** to the Enrollment Services object's own `certificateTemplates` list membership.
- **GAP:** no Microsoft primary source explicitly states whether a raw LDAP write (bypassing `Add-CATemplate`/certsrv.msc) to the Enrollment Services object's `certificateTemplates` attribute is picked up by a running CertSvc process (a) immediately via the same DS-notification mechanism, (b) on the next request (lazy re-read), or (c) only on a polling interval/service restart. Needs a lab observation: write the attribute via raw LDAP against a running lab CA and attempt an enrollment without restarting CertSvc.

### Minimal override recommendation

- **Needed for the scenario to work:**
  1. Clone Workstation Authentication → "Copy of Workstation" (no EKU override needed — Workstation Authentication already carries Client Authentication by design, per Microsoft's default-template description: "Enables client computers to authenticate their identity to servers" [MS-PRIMARY, same template-concepts table], schema version 2).
  2. Grant Domain Users Full Control on "Copy of Workstation" (identical mechanism/citation as ESC4 §2).
  3. **Do not** add it to the selected CA's `certificateTemplates` (this is the "unpublished" half — confirmed as a deliberate, valid AD CS state since nothing in MS-WCCE/MS-CRTD requires a template to be published to exist or to be ACL'd).
  4. Grant `Authenticated Users` Full Control on the selected CA's Enrollment Services AD object (the ESC5 half) — this is a **separate** object/grant from the per-template ACE in step 2, per the ESC5 citation above.
- **Inherited baggage to strip:** none identified — Workstation Authentication's defaults (Client Auth EKU, schema v2, Computer subject type) are exactly what the chain needs; the vulnerability is entirely in the two ACL grants (template FullControl + Enrollment-Services FullControl), not in any attribute override.

## 5. Cross-cutting: default template ACLs — can Web Server / SubCA / Workstation Authentication / User be read/enrolled by low-privileged principals out of the box?

- **Primary-source gap, confirmed:** Microsoft does not publish a default-ACL table for built-in certificate templates (the `certificate-template-concepts.md` table covers purpose/key-usage/publish-to-AD/version only, no security-descriptor column). No MS-CRTD/MS-WCCE page documents default DACLs either (`ntSecurityDescriptor` is specified structurally — [MS-CRTD: ntSecurityDescriptor Attribute](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-crtd/55f06654-8642-4b54-97cf-60c241c218e2) — but carries no stated default value).
- The one directly relevant data point found: "Figure 6 - The default 'User' certificate template security descriptor granting Domain Users the Certificate-Enrollment extended right." [WHITEPAPER] p.23. This is consistent with — and is the primary-source basis for — the shared constraint's assumption that `User` already allows `Domain Users` to enroll by default (hence "stop with a prerequisite error if Domain Users cannot enroll through it" rather than "grant it," since granting it would violate "do not change its ACL").
- For Web Server, SubCA, and Workstation Authentication specifically: **no equivalent screenshot/citation found in the whitepaper or any MS doc.** Community convention (unccitable as primary) holds that non-"Published to AD DS" computer-subject templates like these typically restrict Enroll to administrative groups (Domain Admins/Enterprise Admins/local Administrators) with `Authenticated Users` limited to Read only — which would explain *why* the approved inventory's "Required added rights" column explicitly calls for **new** Domain-Users/Authenticated-Users Enroll grants on every destination template (if Enroll were already open by default, the table wouldn't need to list it as a required addition). This is a **coherent, self-consistent inference**, not a sourced fact. **GAP → lab observation required**: capture the real ACL (`Get-Acl`/`dsacls`/`certutil -v -dstemplate`) of Web Server, SubCA, Workstation Authentication, and User on a vanilla AD CS install to confirm defaults before building the cloning logic's "copy permissions" step, since "copy the source's ACL, then add the listed ACEs" only behaves safely if the source ACL is known.

## Open questions for the human

1. **Default ACLs for Web Server, SubCA, and Workstation Authentication are undocumented by Microsoft.** A lab capture against a reference AD CS install is needed before the "copy the source template's security descriptor, then add overrides" cloning logic can be implemented safely — otherwise the copy step risks inheriting unknown pre-existing Enroll grants (e.g., if a source template unexpectedly already grants some broad group Enroll) or, conversely, assuming a baseline that isn't actually what's copied.
2. **Web Server's literal default EKU set** is not found in any Microsoft primary document (only the Administrator template has a published worked example). Needs the same lab capture as #1 to confirm ESC1's "added by mistake" framing (i.e., that Web Server starts with Server-Auth-only and the clone adds Client Auth on top, rather than replacing an already-broader set).
3. **Live-reload timing for `certificateTemplates` writes (§4):** confirmed that Microsoft's own publish/unpublish workflow doesn't mention a restart, but whether a *raw LDAP* write (bypassing `Add-CATemplate`) is picked up immediately vs. on next request vs. on a poll timer is not documented and needs a lab test — relevant to whether the "unpublished" scenario's later on-CA activation (if ever demonstrated) behaves as expected without a CertSvc restart.
4. **ESC1 post-KB5014754 viability** depends on whether a client tool can supply a client-chosen SID extension alongside an `ENROLLEE_SUPPLIES_SUBJECT` request and have the CA accept it verbatim (MS-WCCE rule 4 is permissive but doesn't fully specify whether the policy module validates/rejects client-supplied SID extension values) — a lab check would settle whether the ESC1 scenario "still bites" in Full Enforcement mode as currently designed, or whether it needs a companion note that strong-mapping must be in Compatibility/Audit mode for the lab to demonstrate it end-to-end.
