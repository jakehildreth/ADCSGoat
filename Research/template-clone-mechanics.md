# Template Clone Mechanics — Research Findings

**Scope:** primary-source evidence for live-template cloning of built-in pKICertificateTemplate objects (Web Server, SubCA, Workstation Authentication, User) via raw System.DirectoryServices.DirectoryEntry, for ADCSGoat issue #19. Pure research; no AD writes, no code changes made.

Legend: [MS] = Microsoft primary source (Learn/open-specs/support/.NET docs or .NET runtime source). [COMMUNITY] = practitioner/community source, cited only as corroboration, never as sole authority. [INFERENCE] = reasoning built on cited primary facts, not stated verbatim by Microsoft. [LAB-OBSERVATION-NEEDED] = claim only confirmable by running it against a real forest.

## 1. Identity / system-managed attribute exclusion list

pKICertificateTemplate is a direct subclass of top ([MS], PKI-Certificate-Template class, learn.microsoft.com/en-us/windows/win32/adschema/c-pkicertificatetemplate -- 'Subclass of: Top'). Its own schema-defined (non-inherited) content attributes are exactly: flags, revision, pKICriticalExtensions, pKIDefaultCSPs, pKIDefaultKeySpec, pKIEnrollmentAccess, pKIExpirationPeriod, pKIExtendedKeyUsage, pKIKeyUsage, pKIMaxIssuingDepth, pKIOverlapPeriod, and (added in the Windows Server 2003 schema update) msPKI-Certificate-Application-Policy, msPKI-Certificate-Name-Flag, msPKI-Certificate-Policy, msPKI-Cert-Template-OID, msPKI-Enrollment-Flag, msPKI-Minimal-Key-Size, msPKI-Private-Key-Flag, msPKI-RA-Application-Policies, msPKI-RA-Policies, msPKI-RA-Signature, msPKI-Supersede-Templates, msPKI-Template-Minor-Revision, msPKI-Template-Schema-Version ([MS], same page; schema-update provenance confirmed in MS-WCCE Appendix B section <3>/<4>, learn.microsoft.com/en-us/openspecs/windows_protocols/ms-wcce/c8bec234-0a53-4a7c-859d-2bb7b2537da5). All of these are safe/required to copy -- they are the template's actual policy payload.

Everything else the object exposes is inherited from top and is either identity, DSA-maintained/constructed, or ACL state:

| Attribute | Classification | Why it must not be copied verbatim | Citation |
|---|---|---|---|
| cn / RDN | Identity | RDN attribute; AD requires RDN-values of siblings to be distinct; set only to the new destination name | [MS] MS-ADTS Constructed/RDN section, learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/85397795-f089-4807-89be-24822570bc2c |
| name | Identity (special behavior) | Even if an object is renamed, the name attribute remains equal to the object's RDN attribute -- not a schema constructed attribute but behaves like one; DSA sets it from the RDN | [MS] same MS-ADTS page |
| distinguishedName | Identity (computed) | Not declared as a constructed attribute, but it behaves like one -- has no independent storage, is derived from parent chain | [MS] same MS-ADTS page |
| objectGUID | Identity | Described as having special behavior; assigned once at creation and immutable | [MS] same MS-ADTS page |
| instanceType, objectCategory, objectClass | Identity/structural | Mandatory, DSA/schema-derived flags describing the object's class and NC role, not meaningful copied from a different object instance | [MS] PKI-Certificate-Template / ms-PKI-Enterprise-Oid class pages (marked Mandatory: True, derived from Top) |
| whenCreated, whenChanged, uSNCreated, uSNChanged, dSCorePropagationData | DSA-maintained/constructed | Replication/versioning metadata written by the DSA on every originating write; a new object always gets fresh values | [MS] MS-ADTS Constructed Attributes page (general constructed-attribute behavior); these specific attributes are standard DSA-metadata attributes listed as inherited-from-Top on every schema class page fetched |
| nTSecurityDescriptor | Security state -- handled separately | Must be read from source and explicitly re-applied to the destination through ObjectSecurity/ActiveDirectorySecurity, not pushed through the generic per-property copy loop (see section 4) | [MS] Win32 'How Security Descriptors are Set on New Directory Objects', learn.microsoft.com/en-us/windows/win32/ad/how-security-descriptors-are-set-on-new-directory-objects |
| showInAdvancedViewOnly | Cosmetic UI flag, not identity | Not dangerous to copy, but the local reference doc skips it anyway (harmless over-exclusion) | -- |
| displayName | Content, but must differ per destination | Must be explicitly overwritten with the destination's own display name (doc does this correctly) | -- |

Assessment of the local doc's skip list (cn, name, objectClass, objectGUID, distinguishedName, instanceType, whenCreated, whenChanged, uSNCreated, uSNChanged, dSCorePropagationData, nTSecurityDescriptor, objectCategory, showInAdvancedViewOnly, displayName, msPKI-Cert-Template-OID): this list is substantially correct against the primary schema references above -- every true identity/constructed/DSA-maintained attribute is present, and there are no missing dangerous attributes based on the actual pKICertificateTemplate schema attribute set. The one structural omission is not in this list at all: the doc never creates the companion msPKI-Enterprise-Oid object that a real OID requires (see section 2) -- that is an OID-minting gap, not an attribute-copy gap.

## 2. Template OID allocation

Primary-source fact: Microsoft's own Win32 API documentation for certificate-policy OID groups states the numeric body of OIDs under the Microsoft PKI arc 'represents a randomly generated numeric sequence that is unique for each forest' ([MS], ObjectIdGroupId, learn.microsoft.com/en-us/windows/win32/api/certenroll/ne-certenroll-objectidgroupid). That forest-unique value is generated once (effectively, the first time AD CS/certificate templates are used in the forest) and is stored as the msPKI-Cert-Template-OID attribute on the CN=OID,CN=Public Key Services,CN=Services,<ConfigNC> container itself -- this container object's own OID value is the forest's base arc, e.g. 1.3.6.1.4.1.311.21.8.3025710.4393146.2181807.13924342.9568199.8 [COMMUNITY corroboration, PKI Solutions, pkisolutions.com/object-identifiers-oid-in-pki, consistent with the Microsoft-documented 'unique per forest' design above].

How a new template's OID is actually built (Microsoft's own tooling pattern): Per-template OIDs are not independently re-randomized values slapped under a literal 1.3.6.1.4.1.311.21.8 constant. The documented/observed pattern is: read the forest's existing base OID from the CN=OID container, then append two more random numeric segments to build msPKI-Cert-Template-OID, and create a new ms-PKI-Enterprise-Oid child object under that same CN=OID container whose own cn and msPKI-Cert-Template-OID attribute record the mapping (this container object is what the Certificate Templates MMC snap-in and certutil read to resolve OID to display name, and is schema-defined with Possible Superiors: Container, ms-PKI-Enterprise-Oid -- [MS] ms-PKI-Enterprise-Oid class, learn.microsoft.com/en-us/windows/win32/adschema/c-mspki-enterprise-oid). This two-part mechanism (forest base + random suffix, plus a companion OID-container object) is implemented explicitly in the widely-used community ADCSTemplate PowerShell module's New-TemplateOID function, which reads CN=OID,...'s msPKI-Cert-Template-OID and constructs the forest value plus two random parts, then calls New-ADObject to create the ms-PKI-Enterprise-Oid object before creating the template itself [COMMUNITY, powershellgallery.com/packages/ADCSTemplate/1.0.1.0/Content/ADCSTemplate.psm1 -- inline comment explicitly states: this function does not use the official (complicated) API for PKI management; instead it creates the exact same AD objects that are generated by the API, including AD forest-specific OIDs].

MS-WCCE on OID freshness (what IS protocol-documented): msPKI-Template-Template-OID, revision, and msPKI-Template-Minor-Revision exist specifically to let clients detect whether a cached template is stale; the protocol spec explicitly leaves the uniqueness-generation algorithm to the implementation (if a customer who modifies a template would like to distinguish the new template from the previous one, that customer either can generate a new OID for the modified template, or can give the new template a higher major or minor revision value -- [MS] MS-WCCE Template IDs, learn.microsoft.com/en-us/openspecs/windows_protocols/ms-wcce/0480bc06-446a-449d-9fdf-a3ba0d44333b). The exact per-template OID-generation algorithm used internally by certsrv.dll/the MMC snap-in is not published in any MS-CRTD/MS-WCCE protocol section -- the forest-base-plus-random-suffix-plus-OID-container-object pattern above is the best-documented reconstruction of that undocumented internal algorithm, corroborated by two independent community sources and consistent with Microsoft's own 'unique per forest' statement, but it is not itself an MS-CRTD/MS-WCCE normative algorithm. Treat the exact digit-count/placement of the random segments as [LAB-OBSERVATION-NEEDED]; the structural requirement (derive from the forest's CN=OID base, and create a companion ms-PKI-Enterprise-Oid object) is well-corroborated.

Verdict on the local doc's scheme (literal arc 1.3.6.1.4.1.311.21.8 plus a single Get-Random -Minimum 100000 -Maximum 999999, no OID-container object): deviates from Microsoft's own design in two ways -- (a) it hardcodes the literal arc instead of reading the forest's actual, already-assigned base OID from CN=OID,CN=Public Key Services,..., so it is not actually forest-unique (collision risk across forests/labs reusing the same doc, and it silently diverges from whatever other templates in the same forest use); (b) it never creates the companion ms-PKI-Enterprise-Oid object, so the new template's OID has no resolvable display-name/localization entry that MMC and certutil expect to find. Neither of these breaks basic enrollment (the CA only needs a syntactically valid, non-colliding OID stored on the template object itself), but both are deviations from the documented/observed Microsoft pattern and should be called out as such, not presented as equivalent.

## 3. Schema version / minor revision semantics

Primary-source facts:
- msPKI-Template-Schema-Version 'defines the pKICertificateTemplate class version and instructs the client and server as to those processing rules that apply to the object' ([MS] MS-WCCE Appendix B section <3>, learn.microsoft.com/en-us/openspecs/windows_protocols/ms-wcce/c8bec234-0a53-4a7c-859d-2bb7b2537da5).
- msPKI-Template-Minor-Revision lets 'the certificate template revision number has two parts (revision and msPKI-Template-Minor-Version)' and is used to identify the minimum revision required in a WCCE request (same citation).
- Product-behavior note <4> on that same page: 'the MMC Certificate Templates snap-in ... automatically increments the minor revision value with each modification of a certificate template.' This is GUI/tool behavior, not a protocol requirement -- the wire protocol and the directory schema do not themselves mandate any particular revision-increment policy.
- Client processing rules keyed off the schema-version value are explicitly enumerated in MS-WCCE Appendix B section <47> (same URL): value absent or 1 -> all Windows versions can use the template; 2 -> Windows XP/Server 2003/Vista+ can use it; 3 -> Windows 2000/XP/Server 2003 cannot; 4 -> only Windows 8/Server 2012+ can use it; other values are ignored by existing clients.
- Default certificate-template versions per built-in template: Web Server = 1, User = 1, Subordinate Certification Authority = 1, Workstation Authentication = 2 ([MS] Certificate template concepts, learn.microsoft.com/en-us/windows-server/identity/ad-cs/certificate-template-concepts, 'Default certificate templates' table -- this table's 'Template version' column is the schema-version concept above).

What this means for blindly copying the source's schema version on a clone: because the schema-version compatibility table above is purely additive (v1 is the most universally compatible; v2 narrows the client set slightly; higher values narrow further), copying Workstation Authentication's v2 value onto its clone, and copying Web Server/User/SubCA's v1 value onto their clones, has no functional downside -- the clone simply inherits the same client-compatibility floor as its source, which is exactly the compatibility envelope the scenario already targets (e.g. the schema-v1 User-template-chain scenario explicitly wants v1 behavior preserved). There is no GUI-only magic beyond the auto-incrementing minor revision counter (note <4> above), which exists purely so already-enrolled clients can detect that a template changed since their last request -- it has no effect on which clients can use the template at all. [INFERENCE]: since the clone is a brand-new object (fresh OID per section 2, fresh revision/msPKI-Template-Minor-Revision starting state is irrelevant because no client has cached anything from it yet), there is no compatibility reason to force a minor-revision bump on creation; it only matters once the clone itself is later modified in place.

## 4. Security descriptor copy semantics (S.DS)

Primary-source fact -- AD does NOT auto-copy a sibling object's ACL on creation. Per the Win32 AD security doc (learn.microsoft.com/en-us/windows/win32/ad/how-security-descriptors-are-set-on-new-directory-objects): if you do not explicitly specify a security descriptor when creating a new object, 'the system builds the object's DACL by merging any inheritable ACEs from the parent object into the default DACL from the classSchema object for the object's class.' For pKICertificateTemplate, that default DACL is the fixed schema-defined value D:(A;;RPWPCRCCDCLCLORCWOWDSDDTSW;;;DA)(A;;RPWPCRCCDCLCLORCWOWDSDDTSW;;;SY)(A;;RPLCLORC;;;AU) ([MS], same PKI-Certificate-Template class page -- 'Default Security Descriptor'), merged with whatever is inheritable from CN=Certificate Templates,.... A plain Children.Add('CN=...', 'pKICertificateTemplate') followed by CommitChanges() therefore gets the schema default plus container-inherited ACEs -- never the source template's explicit ACEs -- confirming the task brief's premise that permissions must be explicitly copied, not assumed automatic.

Owner/Group: per the same Win32 doc, if you don't set them explicitly, 'the owner in a default security descriptor is set to the default owner SID from the primary or impersonation token of the creating process' (typically BUILTIN\Administrators if the creator is a domain-admin-equivalent account) -- never the source object's owner. To truly match the source, owner/group must be explicitly copied too.

.NET mechanics confirmed from the actual runtime source (DirectoryEntry.cs, github.com/dotnet/runtime/blob/main/src/libraries/System.DirectoryServices/src/System/DirectoryServices/DirectoryEntry.cs):
- DirectoryEntry.ObjectSecurity is a plain get/set property backed by a private ActiveDirectorySecurity field; the setter unconditionally sets an internal _objectSecurityModified = true flag and calls CommitIfNotCaching().
- SetObjectSecurityInCache() (the method that actually persists the SD) writes _objectSecurity.GetSecurityDescriptorBinaryForm() -- i.e. the entire binary security descriptor (Owner + Group + DACL + SACL + control flags, including the SE_DACL_PROTECTED/inheritance-blocking bit) -- into the ntSecurityDescriptor property, as one atomic blob, whenever _objectSecurityModified or _objectSecurity.IsModified() is true.
- Practical consequence: if the code does `var srcSd = srcEntry.ObjectSecurity; destEntry.ObjectSecurity = srcSd; destEntry.CommitChanges();`, this copies owner, primary group, the full DACL (including any already-materialized inherited ACEs baked into the source's stored SD), the SACL, and the DACL-protected/inheritance-blocking control bit all in one write -- there is no partial-section copy by default. ActiveDirectorySecurity/ObjectSecurity's AccessControlSections-based Persist/SetSecurityDescriptorBinaryForm(byte[], AccessControlSections) overloads exist if a narrower (DACL-only, or DACL+Owner) copy is ever wanted ([MS] ActiveDirectorySecurity/ObjectSecurity class docs, learn.microsoft.com/en-us/dotnet/api/system.directoryservices.activedirectorysecurity and inherited ObjectSecurity members), but the straightforward whole-object assignment pattern already does what 'copy source permissions' asks for, including the inheritance-protection bit -- no extra explicit handling of AreAccessRulesProtected/inheritance-blocking-style flags is needed beyond doing the whole-SD copy, because it's already part of the same binary blob.
- Caveat [INFERENCE]: because AD's object-creation-time DACL-merge rule (the system merges any inheritable ACEs from the parent object into the specified DACL unless SE_DACL_PROTECTED is set, per the same Win32 doc) applies even when you do supply an explicit SD, and because both source and destination templates live under the same CN=Certificate Templates parent, this merge is a no-op for any ACEs the source already inherited from that same container -- but if the destination is later moved to a different container, or if the source's protected-bit state differs from what's desired for the destination, that must be verified, not assumed.

## 5. Update vs. replace semantics for an owned destination

No single Microsoft document states a definitive always-do-X policy here; the following are the concrete, cited mechanical tradeoffs between the two paths.

(a) In-place update (keep objectGUID/OID, patch attributes + ACL):
- Already-issued certificates are unaffected by definition -- nothing about an issued cert references the live AD object; it references the template name and, via the Certificate Template Information extension, the OID plus major/minor revision that was live at issuance time ([MS] MS-WCCE section 2.2.2.7.7.2, referenced from MS-WCCE Appendix B context). Revoking/reissuing is unaffected by in-place template edits.
- certificateTemplates publication entries reference the template by its cn/short name string on the pKIEnrollmentService object (Certificate-Templates attribute -- [MS] PKI-Enrollment-Service class, learn.microsoft.com/en-us/windows/win32/adschema/c-pkienrollmentservice), not by OID or objectGUID. An in-place update that keeps the same cn therefore requires no republish step -- the CA's issuance-list entry still resolves correctly.
- CA-side caching risk, Microsoft-documented: the 'Rename a custom template' procedure in Manage Certificate Templates explicitly states that after a rename (an in-place DN/CN change) of an already-published template, you must remove it from every issuing CA, restart the Active Directory Certificate Services service (CertSvc) on the affected CAs, and publish the renamed template again ([MS], learn.microsoft.com/en-us/windows-server/identity/ad-cs/manage-certificate-templates, 'Rename a custom template' section). This is direct Microsoft evidence that the CA caches template identity/definition state in a way that is not always transparently refreshed for structural changes to a published template, and a CertSvc restart is the documented remedy. A pure in-place content update (same cn, changed msPKI-*/pKI* values) is not explicitly covered by this warning, but the same doc separately instructs to allow AD DS replication to complete before you publish and test the template for any new/changed template -- i.e. expect at least a replication-latency window, and if symptoms resembling stale template data appear, the documented troubleshooting lever is a CertSvc restart on the affected CA(s), not a forced OID change.
- Publishing/unpublishing itself is documented as separate from both of the above: 'Publish a template to an issuing CA' only changes the CA's issuance list and explicitly doesn't publish issued certificates to AD DS and doesn't touch the template object itself ([MS], Manage Certificate Templates, 'Understand the three publication operations' table).

(b) Delete + full recreate (new objectGUID, new OID via DeleteTree()/Remove-ADObject + fresh add):
- DirectoryEntry/DirectoryEntries expose a DeleteTree() method that removes an entire subtree in one LDAP delete operation ([MS], learn.microsoft.com/en-us/dotnet/api/system.directoryservices.directoryentry, Methods table). For a pKICertificateTemplate leaf object with no children this is equivalent to a normal delete.
- Any CA that already published the old object's cn as a certificateTemplates entry is unaffected at the attribute-value level (same string, same entry) but the delete removes the live template object the CA actually needs to read -- so a recreate-with-same-cn-but-new-OID still requires the CA to successfully resolve that cn to a (now different) template object; per 'CA can't use a certificate template' troubleshooting doc, a CA that cannot read/resolve the current template object (e.g. during the gap between delete and recreate, or because of a transient replication gap) fails enrollment with CERTSRV_E_UNSUPPORTED_CERT_TYPE / Event ID 53/77 ([MS], learn.microsoft.com/en-us/troubleshoot/windows-server/certificates-and-public-key-infrastructure-pki/ca-cant-use-certificate-template).
- A fresh OID means any client/CA cache keyed by the old OID+revision (per the MS-WCCE freshness fields discussed in sections 2/3) is now stale by design -- this is the intended behavior of treating it as a new template, at the cost of a guaranteed republish step (the manage-certificate-templates 'Delete a certificate template' + 'Publish a template to a CA' sequence, both documented as explicit separate operations).
- Deletion does not retroactively affect already-issued certificates (deletion doesn't revoke already issued certificates -- [MS], Manage Certificate Templates, 'Delete a certificate template' section) -- this matches path (a)'s unaffected-certs property, so neither path endangers previously issued certs; the difference is entirely in republish/cache mechanics, not in existing-certificate validity.

Net tradeoff [INFERENCE from the above primary facts]: in-place update is cheaper (no republish needed if cn is preserved) but has a Microsoft-documented precedent (CertSvc restart requirement after rename) suggesting the CA's in-memory template cache is not always automatically coherent with AD-side structural changes; delete+recreate is guaranteed-clean (new OID, no risk of stale cached state) but mandatorily requires removing and republishing on every CA that had it published, and briefly exposes a window where the CA cannot resolve the cn at all. Which is preferred for ADCSGoat's teardown/redeploy workflow is a design choice, not something these facts dictate -- see Open Questions.

## 6. What must be recorded to support clean teardown/restoration

Per Microsoft's AD CS object model (schema pages cited below), the two independent pieces of forest state that ADCSGoat's four scenarios touch, and that must be snapshotted before any CA-level change for restoration purposes, are:

1. The Enrollment Services object for the selected issuing CA -- class pKIEnrollmentService, found at CN=<CAName>,CN=Enrollment Services,CN=Public Key Services,CN=Services,<ConfigNC> ([MS], learn.microsoft.com/en-us/windows/win32/adschema/c-pkienrollmentservice). Its Certificate-Templates attribute (ldapDisplayName certificateTemplates) is the multivalued list of template cns the CA will issue -- this is exactly what ADCSGoat's Publish-AGCertifcateTemplate.ps1 already reads/writes via PutEx. Record the full pre-change value list before adding/removing entries, so publication state can be restored exactly (order is not semantically significant, but the exact member set is).
2. That same pKIEnrollmentService object's nTSecurityDescriptor -- this is the AD-object-level ACL that governs who can write to the CA's AD object (including certificateTemplates itself, and any flags/EditFlags-style attributes if present), which is precisely the object the 'Unpublished ESC4 + ESC5 publication chain' scenario grants Authenticated Users Full Control on per the issue's own constraint ladder (Authenticated Users receives Full Control on that CA's directory object that holds certificateTemplates; do not substitute permissions on the CA host or service). Record the full pre-change SD (binary form or SDDL) before granting, using the same ObjectSecurity/GetSecurityDescriptorSddlForm mechanism described in section 4, so it can be restored byte-for-byte rather than merely removing the one ACE that was added (which risks missing any ordering/inheritance-bit side effects of the add).
3. Separately, any template object's own nTSecurityDescriptor (e.g. the new clone's ACL after scenario-specific rights are layered on) should be recorded for the same reason, though this is implied by the existing 'Generated by ADCSGoat'-tagged ownership model rather than being a new requirement.

Microsoft's own tooling draws exactly this same two-surface distinction: Add-CATemplate/Remove-CATemplate/Get-CATemplate (ADCSAdministration module) operate purely on the CA's issuance list (i.e. surface 1 above -- learn.microsoft.com/en-us/windows-server/identity/ad-cs/manage-certificate-templates, 'Publish a template to a CA' / 'Remove a template from a CA' sections), while template creation/ACL edits are a wholly separate operation performed via the Certificate Templates snap-in or raw LDAP against the template object itself -- reinforcing that these two kinds of AD state (CA issuance list + CA object ACL, vs. template object + template object ACL) are independent restoration units.

## Open questions for the human

- Update vs. replace policy for an owned (Generated by ADCSGoat) destination collision -- section 5 above lays out the mechanical tradeoffs (in-place keeps OID/GUID stability and needs no republish if cn is unchanged, but Microsoft documents a CA-cache/CertSvc-restart quirk after structural changes; delete+recreate is guaranteed-clean but mandates an explicit remove+republish cycle on every CA that had it published). Which default behavior to implement, and whether to expose both as options, is the human's call, not something these facts dictate.
- Whether to adopt the forest-base-OID-plus-ms-PKI-Enterprise-Oid-companion-object pattern (matching Microsoft's own tooling, per section 2) versus a simpler ADCSGoat-only convention (e.g. a fixed sub-arc reserved for ADCSGoat-generated templates) -- both are workable for a lab tool; the former is more authentic to real Microsoft behavior, the latter is simpler to implement/teardown. This is a design tradeoff, not a correctness requirement, since functional enrollment only needs OID uniqueness.
- Exact digit-count/format of the per-template OID suffix is [LAB-OBSERVATION-NEEDED] -- no MS-CRTD/MS-WCCE section documents the internal algorithm; only the unique-per-forest design intent is Microsoft-confirmed. If byte-for-byte fidelity to real Microsoft-generated OIDs matters to the scenario design, a lab capture against a real forest (or further corroboration from additional independent community implementations) is recommended before finalizing.
- Whether in-place template-content updates (not renames) also require a CertSvc restart on the issuing CA is not explicitly documented by Microsoft (only the rename case is) -- worth a lab check if the owner cares about update-path reliability without a CA service restart.
- Owner/Group copy scope -- section 4 shows that a whole-ObjectSecurity assignment copies Owner+Group+DACL+SACL+protection-bit atomically. Confirm whether the scenario design wants the clone's Owner/Group to literally match the source (likely BUILTIN\Administrators/Domain Admins, harmless) or whether the creating account's own identity should remain owner -- this is a cosmetic choice with no functional AD CS impact either way, but is the human's call.
